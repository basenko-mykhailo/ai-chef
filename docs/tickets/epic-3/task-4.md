# Епік 3.4 — Service `RecipePromptBuilder` (+ 3.5 Recipe JSON schema)

> Заповнено: 2026-06-10 · Джерело: `docs/tickets/plan.md`

## 1. Опис задачі (з plan.md)

**3.4:** Метод приймає `User`, масив обраних `FamilyMember`-ів і повертає system + user prompts. Включає інструкції: "повертай JSON-схему", "інтерпретуй алергії широко", "одиниці — як у коморі".

**3.5 (включено сюди за рішенням користувача):** Зафіксувати очікувану структуру відповіді Claude: `{name, description, ingredients: [{name, quantity, unit, in_pantry: bool}], steps: [], kbju: {kcal, protein, fat, carbs}, servings}`. Документація — в коді як константа.

## 2. Додатковий контекст

Користувач: **включити константу JSON-схеми (тікет 3.5) у цей тікет**, решта — дефолти. Дефолти, зафіксовані явно:

- `app/Services/RecipeSchema.php` — окремий клас: канонічна структура відповіді як константа (для вставки в промпт) + константи обов'язкових ключів (`REQUIRED_KEYS`, `INGREDIENT_KEYS`, `KBJU_KEYS`) — їх споживатиме парсер 3.6.
- `app/Services/RecipePromptBuilder.php` — `build(User $user, array $members, array $pantry): array{system: string, user: string}`.
- **Комора як plain-масив** `[['name' => ..., 'quantity' => ..., 'unit' => ...], ...]` — `PantryItem` (Епік 1) ще не існує; коли 1.4 з'явиться, 3.8 просто змапить модель у цей масив. `User` лишається в сигнатурі за планом (майбутнє джерело комори/локалі), зараз даних з нього не беремо.
- Промпти українською. Правила з PRD (§3.1, §3.3), які мають бути в system-промпті:
  - повертай **лише валідний JSON** за структурою з `RecipeSchema` (без markdown/пояснень);
  - **алергії інтерпретуй широко** ("горіхи" → арахіс, кешью, фундук, мигдаль…); якщо є сумнів щодо безпечності — виключай (PRD: безпека алергій — пріоритет);
  - обмеження всіх обраних членів **комбінуються через AND**;
  - **одиниці інгредієнтів — ті самі, що в коморі** (enum: г, кг, мл, л, шт, ст.л., ч.л., склянка);
  - дозволено 1-2 базові інгредієнти не з комори (сіль/олія/спеції) з `in_pantry: false`;
  - КБЖУ — на порцію.
- Edge-дефолти: порожній `$members` → блок обмежень опускається (готуємо "для себе"); порожні текстові поля члена сім'ї пропускаються; улюблені — "намагайся врахувати", неулюблені — "уникай", алергії/дієти — "суворо виключай".

## 4. Скоуп

**В скоупі:**
- `RecipeSchema`: `STRUCTURE` (heredoc-приклад структури для промпта), `REQUIRED_KEYS`, `INGREDIENT_KEYS`, `KBJU_KEYS`, `ALLOWED_UNITS` (г/кг/мл/л/шт/ст.л./ч.л./склянка).
- `RecipePromptBuilder::build()`: system-промпт з усіма правилами §2; user-промпт зі станом комори (рядки `назва — кількість одиниця`) і обмеженнями обраних членів (ім'я + три поля, порожні пропущено).
- Юніт-тести: структура повернення; присутність ключових інструкцій у system; комора і члени в user; edge-кейси (0 членів, порожні поля, порожня комора).

**НЕ в скоупі** (буде в наступних тікетах / поза MVP):
- Виклик Claude і парсинг відповіді (3.6), Job/endpoint (3.8), кеш (3.9), UI (3.7/3.10).
- Підбір/тюнінг якості промпта на живих генераціях — ітеруватиметься в 3.8/3.11.

## 7. Acceptance criteria

- [ ] `RecipeSchema` фіксує структуру `{name, description, ingredients: [{name, quantity, unit, in_pantry}], steps: [], kbju: {kcal, protein, fat, carbs}, servings}` як константу + масиви обов'язкових ключів і дозволених одиниць.
- [ ] `build(User, array $members, array $pantry)` повертає `['system' => string, 'user' => string]`, обидва непорожні, українською.
- [ ] System-промпт містить: інструкцію "лише JSON" зі структурою з `RecipeSchema`, широку інтерпретацію алергій з прикладом "горіхи", AND-комбінацію, перелік дозволених одиниць, правило 1-2 staples з `in_pantry: false`, КБЖУ на порцію.
- [ ] User-промпт містить кожну позицію комори з кількістю та одиницею і кожного обраного члена з його непорожніми обмеженнями; порожні поля не дають порожніх рядків.
- [ ] 0 обраних членів → user-промпт без блоку обмежень, build не падає; порожня комора → build не падає.
- [ ] `composer test` — нові тести + повний suite зелені.

## 8. Ризики / відкриті питання

- Якість промпта (чи стабільно Haiku 4.5 повертає валідний JSON у цій структурі) перевіриться лише на живих генераціях у 3.8 — очікуване місце для ітерацій; 3.6 додасть retry на невалідний JSON.
- `User $user` зараз не використовується всередині build (лише сигнатура за планом) — задокументовано; з Епіком 1 стане джерелом комори.
